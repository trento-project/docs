== Summary

Let users run operations and checks executions at a time of their choice, once or periodically, for one target or for a set of targets, and let them define maintenance windows in which Trento does not act on a part of their landscape.

Scheduling and maintenance windows live in Trento Web. Three implementations of the same HTTP API were built to compare how schedules are stored and fired: keep https://github.com/quantum-elixir/quantum-core[Quantum], replace it with https://github.com/oban-bg/oban[Oban], and event sourcing with Commanded. One frontend works on all three. The choice between them is to be decided.

== Motivation

Four features ask Trento to act, or not to act, at a given time, without a user clicking a button:

* *Operations scheduling*: request an operation (reboot a host, start a SAP system, put a cluster in maintenance, ...) for one target at a future date and time, once or periodically, with the same preconditions as a manual request.
* *Bulk scheduling*: schedule the same operation for a set of targets in one step.
* *Customization of check execution frequency*: today every registered host and cluster runs its checks every 5 minutes. Users want to change the global frequency (environment variable, helm flag, Settings view) and override it per host or cluster.
* *Maintenance windows*: one-time or periodic time slots in which Trento does not execute checks, does not run operations, or both, on a target and on the targets that depend on it. A window on a SAP system covers its database, its clusters and all their hosts.

An exception window per host or cluster, in which only the checks of that target are not executed, was the first answer to the last need. It is kept as a fallback (plan B, see link:#_plan_b_exception_window_per_target[Plan B: exception window per target]) in case maintenance windows cannot be delivered.

A fourth feature, *mass/bulk operations*, is related: it requests the same operation for a set of targets now. It is designed and built separately. Bulk scheduling does not depend on it, but reuses its target selection in the UI.

The features share the same building blocks:

* something that fires at a given time and survives restarts
* recurrence rules: every X days, every X weeks on some weekdays, every X months, every X years, with an end condition
* the evaluation of the operation preconditions outside of an HTTP request
* the knowledge of which targets depend on which (the topology), for maintenance windows

This RFC answers:

* which component owns the scheduling: Web, Wanda, or both
* how schedules are stored and fired, and with which library
* which HTTP API the frontend uses. The API stays the same whatever the implementation.
* how scheduled requests interact with the existing messaging between Web, Wanda and the agents
* how maintenance windows cover the targets that depend on the one they are set on, and where Trento enforces them

=== Use Cases Outline

* As a user, I want to schedule an operation for a target at a future date and time, so that it runs in a maintenance window without me being there.
* As a user, I want to schedule an operation periodically (every X days, weeks on some weekdays, months, years) until a date or for a number of occurrences. A target can have several schedules of the same operation.
* As a user, I want to schedule the same operation for several targets at once.
* As a user, I want to see, change and cancel the schedules of a target in its details view.
* As a user, I want the activity log to tell me when an operation was scheduled, when it was requested, and why a scheduled request failed (Trento not available, policies not met, another operation running).
* As an administrator, I want to set the global check execution frequency from the environment, from helm, or from the Settings view.
* As a user, I want a different check execution frequency for a specific host or cluster, or no periodic execution at all.
* As a user, I want to schedule a maintenance window, one-time or periodic, for a host, cluster, HANA database or SAP system, which forbids checks executions, operations, or both.
* As a user, I want a maintenance window to apply to the targets that depend on the one it is set on, and I want overlapping windows to add up.
* As a user, I want to see the scheduled and ongoing maintenance windows of a target, also the ones that come from another target, and to change or delete them.
* As a user, I want to schedule the same maintenance window for several targets at once.
* As a user, I want manual and scheduled requests to be refused during a window that forbids them.

NOTE: Exact UI wording and the premium distinction are product decisions that do not change the architecture described here.

== Detailed design

=== Current state

Scheduling touches the interaction between Web, Wanda and the agents, so a precise picture of today matters.

[width="100%",cols="<20%,<27%,<27%,<26%",options="header"]
|===
| |Web |Wanda |Agent
|Checks execution

|Runs one request at a time: plan, commit, verify, rollback on failure

Facts that matter for this design:

* Wanda has no notion of time. Web owns the target registry, the checks selection, the operation policies, the users and their timezone, the activity log, the alerting and the settings.
* A checks execution request for a group that is already running is rejected by Wanda and dead-lettered to `trento.checks.executions_error`. Web gets no reply. Nothing consumes that queue.
* Web encodes every message with a CloudEvent `expiration` of 5 minutes (`Trento.Contracts.to_event/2`). The agents check it. Wanda does not (`Contracts.from_event/1` with `validate_expiration: false`). If Wanda or RabbitMQ is down, a request waits in the queue and runs whenever Wanda comes back.
* `CHECKS_INTERVAL` exists only in `runtime.exs`, as a number of minutes pasted into a cron expression. It cannot express hours or weeks and is not exposed by helm or ansible.
* Web and Wanda run as a single replica. Web is not clustered.
* Web stores hosts, clusters, SAP systems and databases with Commanded (event sourcing, CQRS). Settings, users and the activity log are plain Ecto tables.

=== Where the scheduling belongs

==== Option 1: Web only

PROs:

* Web already decides when to request: the periodic checks job and every manual request live there
* the data needed at fire time is in Web: targets, selection, policies, users, timezone, activity log
* Wanda and the agents stay as they are: reactive executors
* the inter-service messages do not change

CONs:

* Web gets one more responsibility, the scheduling

==== Option 2: Wanda only

PROs:

* Wanda already orchestrates executions and operations

CONs:

* Wanda knows neither the targets, the users nor the policies. It needs them from Web at fire time, over a channel that does not exist today
* the activity log and the alerting live in Web, so every scheduled outcome travels back to Web anyway

==== Option 3: Both

CONs:

* two schedulers to operate and to keep consistent, for no benefit identified

'''

Proposed option is *Option 1: Web only*. Wanda and the agent need no change to support scheduling. Wanda gets one small hardening change, described in link:#_wanda_changes[Wanda changes].

=== Storing and firing schedules

The three implementations share everything except two things: where a schedule lives, and what fires it at its time. The shared part is:

* the recurrence rules (`Trento.Scheduling.Recurrence`)
* the operation preconditions without an HTTP connection (`Trento.Operations.Requests`), on targets loaded the same way as the operation controllers load them (`Trento.Operations.Targets`)
* the global checks frequency setting
* the HTTP API, described in link:#_http_api[HTTP API]
* the activities the application emits itself, through the activity log pipeline (see link:#_activity_log_and_alerts[Activity log and alerts])
* the record of the runs of the schedules, which traces Wanda's replies back to their schedule

Proof of concept: {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22scheduling%3A%20shared%22%20sort%3Acreated-asc[`scheduling: shared` pull requests], one pull request per item of the list above ({poc-repo}/pull/8[#8], {poc-repo}/pull/9[#9], {poc-repo}/pull/10[#10], {poc-repo}/pull/11[#11], {poc-repo}/pull/55[#55], {poc-repo}/pull/56[#56]).

Every implementation runs the same steps when a schedule is due: check the grace period, run the policies on fresh data, request the operation, log the outcome, then move the schedule to its next occurrence or delete it.

==== Option 1: Keep Quantum

Schedules are rows in Ecto tables, with their `next_run_at`. One Quantum job runs every minute. It selects the due rows with `FOR UPDATE SKIP LOCKED`, runs them, and moves each to its next occurrence. A second Quantum job, also every minute, evaluates the checks executions (see link:#_checks_execution_frequency[Checks execution frequency]).

Proof of concept: {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22scheduling%3A%20quantum%22%20sort%3Acreated-asc[`scheduling: quantum` pull requests]. The runner is in {poc-repo}/pull/18[#18].

PROs:

* no new dependency and no new infrastructure
* one source of truth: the schedule row. Create, change and cancel are plain Ecto writes, in one transaction with their activity log entry
* the UI sets start times to the minute, so a runner at the start of each minute runs schedules on time
* the runner is one cron entry. Moving it to another library later changes one file, not the schedules
* smallest code: about 1600 lines of code and 1700 lines of tests on top of the shared part, 15 new modules

CONs:

* Quantum is not maintained: its last release dates back to February 2024, and its repository receives only automated dependency updates since July 2025
* retries and history are ours. A request that cannot be sent is retried at the next minute until the grace period ends. The activity log is the history
* Quantum keeps no state. Web detects a missed occurrence from `next_run_at` and the grace period

==== Option 2: Oban

Oban replaces Quantum for every periodic job, with its built-in cron. Jobs that run more often than once a minute (the heartbeat check, and the heartbeat faker of the demo) move to a small supervised process with `Process.send_after`. Each schedule row has one pending Oban job at `next_run_at`. The job is inserted, replaced or cancelled in the same transaction as the row. When the job runs, it checks that it is still the pending occurrence, requests the operation, and inserts the job of the next occurrence. A request that cannot be sent snoozes the job for one minute. The checks evaluator is an Oban cron entry.

Proof of concept: {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22scheduling%3A%20oban%22%20sort%3Acreated-asc[`scheduling: oban` pull requests]. Oban replaces Quantum in {poc-repo}/pull/24[#24]. The job per occurrence is in {poc-repo}/pull/30[#30].

PROs:

* persistent jobs, active project (v2.24.2 released in October 2026), Apache-2.0 license. The paid Pro edition is not needed
* precision to the second, retries, pruning, telemetry, and a dashboard (https://github.com/oban-bg/oban_web[Oban Web], Apache-2.0)
* removes the dependency on Quantum

CONs:

* two sources of truth: the schedule row and its job. Every write keeps them in sync, and a job must detect that it is stale
* the grace period check is still necessary: without it, a job delayed by a downtime runs late
* two new tables (`oban_jobs`, `oban_peers`) and a migration
* requires PostgreSQL 14 or later. The oldest PostgreSQL version Trento documents is 14.10 (SLES for SAP 15 SP4)
* about 1950 lines of code and 1850 lines of tests on top of the shared part, 26 new modules

NOTE: An intermediate path exists: the data model of Option 1, with an Oban cron entry as the runner. It removes Quantum without a second source of truth.

==== Option 3: Event sourcing

An operation schedule is a Commanded aggregate (`Trento.Operations.Schedule`). Its commands are: schedule, change, cancel, start a run, complete a run. Recurrence, params and policy errors are value objects in the events, which carry no user: the user travels in the event metadata, and the context logs the user actions as activities after a successful dispatch. A projector writes the `operation_schedules` read model, and the API waits for it (strong consistency) to read its own writes. A Quantum job every minute dispatches "start a run" for the due schedules. The aggregate derives the operation id of the occurrence from the schedule id and the occurrence, and keeps the run pending. The job then runs the policies, requests the operation with that id and dispatches the outcome. A pending run is started again after 30 seconds with the same id, and the aggregate fails it as "Trento not available" after the grace period. A replay of the events never requests an operation again.

The checks interval of a target is an event on the Host and Cluster aggregates, as the checks selection is, carried by their roll-up. A projector writes it to its own read model. The time of the last periodic request stays in a plain table: an event every few minutes for every target adds no value to the event store. A maintenance window is an aggregate of its own, projected into a read model with the same columns as the table of the other options, so the coverage and the enforcement are the same code.

Proof of concept: {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22scheduling%3A%20event%20sourced%22%20sort%3Acreated-asc[`scheduling: event sourced` pull requests]. The aggregate is in {poc-repo}/pull/36[#36], the runs in {poc-repo}/pull/41[#41], the checks settings as host and cluster events in {poc-repo}/pull/43[#43].

PROs:

* follows the architecture of hosts, clusters and SAP systems
* the audit trail and the activity log come from the events
* the removal of schedules with their target is an event handler on the deregistration events
* the checks settings of a target live next to its checks selection
* a fit for future rules that span several operations on one target (Option B of link:#_another_operation_already_running[Another operation already running]), or for a permanent change history of schedules

CONs:

* most code: about 3050 lines of code and 3650 lines of tests on top of the shared part, 41 new modules. Maintenance windows add about 2350 and 1900 lines, against 1700 and 1300 in the other options
* schedules and frequencies are configuration with few rules. No current requirement asks for their event history
* the API answers read their own writes, so every command is dispatched with strong consistency. When the read model does not catch up in time, the change is saved but the API answers `202` without the resource
* changes that span two aggregates or two commands are not atomic, for example a bulk request, or the frequency and the exception window of plan B in one request
* a bulk request spans one aggregate per target, so it is not atomic. All the targets are validated first, then one command per target is dispatched
* the roll-up of hosts and clusters must carry the new fields of their aggregate state
* Commanded has no scheduler, so Quantum still fires the runs. The `commanded_scheduler` library does not compile with Commanded 1.x

==== Other libraries

No other library fits:

* job queues on Redis or Faktory (Exq, BullMQ, faktory_worker_ex) need new infrastructure
* job queues on PostgreSQL other than Oban (Rihanna, EctoJob, Honeydew) show no activity for years
* in-memory schedulers (Periodic, sched_ex) keep nothing across restarts, as Quantum
* https://github.com/dashbitco/broadway[Broadway] is a pipeline that consumes messages from a queue (RabbitMQ, SQS, Kafka). It has no notion of time
* RabbitMQ delayed messages need a plugin that is archived. A delayed message cannot be listed, changed or cancelled
* a GenServer of our own in place of the Quantum job is Option 1 without Quantum. It was not built

=== Recurrence rules

Operation schedules and maintenance windows need the same rules. They are implemented once, in `Trento.Scheduling.Recurrence`, and used by both, and by the exception windows of plan B. Proof of concept: {poc-repo}/pull/8[#8].

Cron expressions are not enough: "every 2 weeks", "every 3 months on the 31st" or "for 5 occurrences" cannot be expressed. RRULE (RFC 5545) libraries exist for Elixir but are not well maintained and implement much more than we need.

A schedule is a start (UTC instant), a timezone (the user timezone at creation time) and an optional recurrence: a frequency (daily, weekly, monthly, yearly), an interval (every X), weekdays (weekly only), and an end condition (an end date, a number of occurrences, or none). Rules:

* occurrences keep the local time of the start across daylight saving time changes (03:00 in Berlin is 01:00Z in summer and 02:00Z in winter)
* a local time that does not exist (spring forward) moves to the first valid time. A local time that exists twice (fall back) uses the first one
* weekly: weeks are counted from the week of the start. With no weekday selected, the weekday of the start is used
* monthly and yearly use the day of the start. On a day the month does not have (31), the occurrence is on the last day of the month. 29 February becomes 28 February in non leap years
* end date: no occurrence on that date or after it, for individual and bulk schedules
* a change of the schedule restarts the count of occurrences. A missed occurrence counts

=== Checks execution frequency

==== Global frequency

* *Environment*: `CHECKS_INTERVAL` takes the new values: `5m`, `15m`, `30m`, `1h`, `6h`, `12h`, `24h`, `1w`, `2w`, `4w` or `disabled`. A number of minutes that matches one of them (`5`, `60`, ...) is still accepted, so existing installations keep working. Any other value stops the boot with an error, as other invalid environment variables already do. When the variable is set, the Settings view shows it read-only, as alerting settings already do (`enforced_from_env`), and the API answers `409` to a change. The variable gets documented, and exposed as a helm value and an ansible variable.
* *Settings*: a new settings entry stores the global frequency. A new ability (`all:checks_execution_settings`) protects it. The change is logged (`checks_execution_settings_updated`), and the setting is an AI assistant tool, like the other settings.
* *Default*: 5 minutes.

Proof of concept: {poc-repo}/pull/10[#10] (backend), {poc-repo}/pull/48[#48] (Settings view).

==== Per target frequency

Each host and cluster can have a frequency override. No override means the global frequency. `disabled` means no periodic execution.

Changing it requires a new ability, `all:check_frequency`, and logs `host_checks_frequency_changed` or `cluster_checks_frequency_changed`. The settings of a deregistered target are removed with it.

Proof of concept: storage in {poc-repo}/pull/20[#20] (Quantum), {poc-repo}/pull/32[#32] (Oban), {poc-repo}/pull/43[#43] (event sourced). API endpoints in {poc-repo}/pull/21[#21], {poc-repo}/pull/33[#33], {poc-repo}/pull/44[#44]. UI in {poc-repo}/pull/49[#49].

==== Evaluation

===== Option 1: one evaluator every minute

A job runs every minute. For each registered host and checkable cluster with selected checks, it requests an execution when the frequency of the target elapsed since its last periodic request, give or take half a minute so that the tick does not stretch the frequency, unless a maintenance window forbids checks executions on the target.

PROs:

* evolution of today's periodic job: same request function, one more filter
* changing a frequency or a window, registering or deregistering a target needs no job management
* a target leaving a maintenance window is executed at the next minute when due

CONs:

* one query over the targets per minute, which is fine for the expected number of targets

===== Option 2: one self-rescheduling job per target

PROs:

* no work when nothing is due

CONs:

* every change (frequency, window, registration, deregistration, selection) must find, cancel and reinsert jobs
* more state to keep consistent

'''

Proposed option is *Option 1*. It is the same in the three implementations. Manual requests (UI, API, AI assistant tools) are refused with a `422` during a maintenance window that forbids checks executions. The UI disables "Start Execution" with a tooltip and shows the time of the next execution, after the windows. The backend computes both, so the rules live in one place.

Proof of concept: {poc-repo}/pull/22[#22] (Quantum), {poc-repo}/pull/34[#34] (Oban), {poc-repo}/pull/45[#45] (event sourced).

==== Overlapping executions

The worry that executions pile up when an execution lasts longer than the frequency does not apply to Wanda: it refuses a second execution for a running group, and its execution timeout is 5 minutes, which is the shortest frequency. What does grow is the dead letter queue, with one rejected message per overlap. With the evaluator, Web records the last periodic request and never sends two requests within one interval, so overlaps only happen at the shortest frequency. Cleaning the dead letter queues (TTL or max length) is a separate, existing issue.

A frequency per check or per group of checks is out of scope. Wanda executes all the selected checks of a group in one execution, and the health of a target is computed from that execution. Running subsets at different frequencies changes that model and needs its own design.

==== Plan B: exception window per target

If maintenance windows cannot be delivered, each host and cluster can have one exception window instead: a start, a duration, a timezone and an optional recurrence, without an end condition. During the window, no periodic checks execution runs against the target, the next execution falls after the window, and a manual execution gets `422` "Checks cannot be executed during exception window". Only checks executions are affected. The window is saved with the frequency of the target (`exception_window` in the checks settings).

The proofs of concept keep it in separate branches on top of the frequency, so that it can be picked up as it is.

Proof of concept: {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22scheduling%3A%20plan%20b%22%20sort%3Acreated-asc[`scheduling: plan b` pull requests], per implementation: {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22scheduling%3A%20plan%20b%22%20label%3A%22scheduling%3A%20quantum%22%20sort%3Acreated-asc[Quantum], {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22scheduling%3A%20plan%20b%22%20label%3A%22scheduling%3A%20oban%22%20sort%3Acreated-asc[Oban], {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22scheduling%3A%20plan%20b%22%20label%3A%22scheduling%3A%20event%20sourced%22%20sort%3Acreated-asc[event sourced], {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22scheduling%3A%20plan%20b%22%20label%3A%22scheduling%3A%20ui%22%20sort%3Acreated-asc[UI].

=== Operations scheduling

==== Schedulable operations

Host reboot, cluster maintenance change (cluster, node or resource), SAP system start and stop, SAP instance start and stop, HANA database start and stop (whole database or site). Other operations, for example applying a saptune solution, make sense once and are not schedulable.

==== Schedules

A schedule holds: the target type and id, the operation and its arguments, the start, the timezone, the recurrence, `next_run_at`, the number of occurrences already run, an optional `bulk_id` and the user who created it. A target can have several schedules of the same operation. SAP instance operations use the SAP system as target, and pass the host and the instance number in the arguments, as the immediate request does in its path.

* *create*: the start must be in the future. The policies run at creation too, but only as information: the schedule is saved, and failing policies come back as `warnings`. They run again at the scheduled time.
* *change*: replace the arguments and the timing. The count of occurrences restarts.
* *cancel*: delete the schedule.
* *run an occurrence*: see below. Then a one-time schedule is deleted. A periodic schedule moves to its next occurrence, or is deleted after the last one.
* *target removed*: the schedules of a deregistered target are deleted. Each deletion logs "operation schedule cancelled", correlated with the clean up.

Proof of concept, create, read, change and cancel: {poc-repo}/pull/13[#13], {poc-repo}/pull/14[#14], {poc-repo}/pull/15[#15], {poc-repo}/pull/16[#16] (Quantum), {poc-repo}/pull/25[#25], {poc-repo}/pull/26[#26], {poc-repo}/pull/27[#27], {poc-repo}/pull/28[#28] (Oban), {poc-repo}/pull/36[#36], {poc-repo}/pull/37[#37], {poc-repo}/pull/38[#38], {poc-repo}/pull/39[#39] (event sourced).

==== Preconditions at fire time

A scheduled request honors the same policies as a manual one. Today they run in `OperationsPolicyPlug`, tied to the HTTP connection. They move to a context function (`Trento.Operations.Requests`) that loads the target with the same data as the controllers, runs the policies and requests the operation. The loaders move out of the controllers (`Trento.Operations.Targets`), so the plug and the context load the same data. Bulk operations need the same function. Proof of concept: {poc-repo}/pull/9[#9].

At fire time:

* *the maintenance windows*: an ongoing window that forbids operations on the target refuses the request. The failure is recorded with the reason "maintenance window".
* *the policies*: agent heartbeat (stale target), saptune state, instances state and the other existing rules, on fresh data. A failure is recorded with the same messages the forbidden modal shows.
* *the creator*: no permission check. The creator's ability is checked when the schedule is created or changed.
* *Trento not available*: the grace period is 5 minutes after the scheduled time, the same as the expiration of operation requests. A request that cannot be sent is retried until the grace period ends. After it, the occurrence is recorded as failed with reason "Trento not available" and is not requested. Missed occurrences are not caught up: the next occurrence is computed after the current time, and the missed ones count as done.
* *the run*: each requested occurrence is recorded with its operation id (`scheduled_operation_runs`, unique per schedule and occurrence). Wanda answers with the operation id only: the run traces the completion, or the refusal, back to the schedule, also after a one-time schedule is gone.
* *robustness*: a schedule that cannot run is logged and does not stop the others. In the Oban implementation a crashed job is retried without requesting twice, and a cron job gives a job back to a schedule that lost its own.

Proof of concept, run at the scheduled time: {poc-repo}/pull/18[#18] (Quantum), {poc-repo}/pull/30[#30] (Oban), {poc-repo}/pull/41[#41] (event sourced).

==== Another operation already running

Web does not know which operations are running: only Wanda does. Two options:

===== Option A: let Wanda decide

Web requests the operation as today. If another operation runs on the same group, Wanda replies `OperationCompleted` with `REQUEST_FAILED/ALREADY_RUNNING`.

PROs:

* no duplicate state, Wanda stays the only source of truth
* no contract change for this case
* the reply carries the `operation_id`, which the "scheduled operation requested" entry also carries. Web records the refusal of a scheduled request as "scheduled operation request failed", reason "another operation running", correlated to the schedule ({poc-repo}/pull/56[#56])

CONs:

* the API cannot answer "already running" synchronously
* Wanda's scope is the `group_id`: a host reboot (group = host) and a cluster host operation on the same host (group = cluster) do not block each other. That is today's behavior

===== Option B: Web keeps its own list of running operations

Web records an operation as requested when it publishes, running on `OperationStarted`, done on `OperationCompleted`, and adds a "no operation running" rule to the policies.

PROs:

* a synchronous answer for manual, scheduled, bulk and API requests, shown in the forbidden modal
* conflicts can be defined per resource, not per `group_id`

CONs:

* a copy of Wanda's state that can drift: a Wanda crash leaves no `OperationCompleted`, so Web needs timeouts, and the step timeouts live in Wanda (a database start can last up to 36 hours). `OperationStarted` needs to carry a `timeout_at`
* check-then-publish races remain, so Option A handling is necessary anyway

'''

Proposed approach: *Option A now, Option B together with bulk operations*.

A scheduled request does not need a synchronous answer. Bulk operations do: the whole bulk request must be refused, through the UI and the API, when one target has an operation running. Option B is therefore planned with bulk operations, once, as one more policy rule in the context function introduced here. The frontend shows "already running" for manual requests from the running operations it already knows.

==== Bulk scheduling

A bulk request creates one schedule per selected target, with the same operation, arguments and timing, and a shared `bulk_id`.

* The policies run per target. Each schedule comes back with its own `warnings`.
* Option 1 and Option 2 insert all the schedules in one transaction: all or nothing. Option 3 validates all the targets, then dispatches one command per target.
* After creation, each schedule lives on its own: it is listed, changed, cancelled and run like an individual one. Its activity log entries carry the `bulk_id`. There is no summary entry for the bulk request.
* Each occurrence is a request for one target, so bulk scheduling does not depend on bulk operations or on Option B. The UI reuses the target selection of bulk operations when it is available.

Proof of concept: {poc-repo}/pull/19[#19] (Quantum), {poc-repo}/pull/31[#31] (Oban), {poc-repo}/pull/42[#42] (event sourced), {poc-repo}/pull/53[#53] (UI).

=== Maintenance windows

==== Windows

A maintenance window is set on a registered host, cluster, HANA database or SAP system. It has a start, a timezone, a duration of up to 31 days and an optional recurrence: every X days, weeks on some weekdays, months or years, until a date or forever. It forbids checks executions, operations, or both.

* A target can have several windows. Windows of the same target, or of targets that depend on each other, can overlap: their restrictions add up.
* A window can be changed at any time, also while it is ongoing: it can keep its start in the past. A change that leaves no occurrence ahead is refused. Such a window is deleted instead.
* The windows of a deregistered target are deleted with it, logged by the system and correlated to the clean up.
* Scheduling, changing and deleting windows requires a new ability, `all:maintenance_windows`. Every user sees them.
* A bulk request sets the same window on up to 500 targets of one type, one window per target with a shared `bulk_id`, all or none.

Proof of concept: create in {poc-repo}/pull/61[#61] (Quantum), {poc-repo}/pull/73[#73] (Oban), {poc-repo}/pull/85[#85] (event sourced), change in {poc-repo}/pull/63[#63] (Quantum), {poc-repo}/pull/75[#75] (Oban), {poc-repo}/pull/87[#87] (event sourced), delete in {poc-repo}/pull/64[#64] (Quantum), {poc-repo}/pull/76[#76] (Oban), {poc-repo}/pull/88[#88] (event sourced), bulk in {poc-repo}/pull/66[#66] (Quantum), {poc-repo}/pull/78[#78] (Oban), {poc-repo}/pull/90[#90] (event sourced).

==== Coverage

A window covers the target it is set on and the targets that depend on it:

* a cluster covers its hosts
* a HANA database covers the cluster that manages it, the hosts of that cluster and its own hosts, in the cluster or not
* a SAP system covers its database (as above), the cluster that manages its ASCS/ERS instances, the hosts of that cluster and its own hosts

A cluster manages a database or a SAP instance when its SAP resources name the SID and the instance number of an instance that runs on one of its hosts. This is how the operation policies already find "the cluster of" a database or an instance.

A window on a host also forbids the operations that act on that host through another target: the cluster host operations (Pacemaker, cluster start and stop on a node) and the SAP instance operations on that host. This is the safest reading of "operations are forbidden on one particular host", and an open question.

The coverage is resolved when it is needed, on the topology Trento knows at that moment:

* from a target up to the targets whose windows cover it, to list the windows of a target and to check an operation
* from the ongoing windows down to the hosts and clusters they cover, once per run of the checks job

A host that joins a cluster during a cluster window is covered by it, an ASCS failover moves the coverage with the instance, and deregistered targets cover nothing. A projection of the covered targets of each window must react to every discovery event that changes the topology, so the proofs of concept do not keep one. Two indexes (`hosts.cluster_id`, `sap_systems.database_id`) support the queries.

Proof of concept: from a target up in {poc-repo}/pull/62[#62] (Quantum), {poc-repo}/pull/74[#74] (Oban), {poc-repo}/pull/86[#86] (event sourced), from the windows down in {poc-repo}/pull/67[#67] (Quantum), {poc-repo}/pull/79[#79] (Oban), {poc-repo}/pull/91[#91] (event sourced).

==== Where Trento enforces them

* *Periodic checks executions*: the checks job skips the hosts and clusters covered by an ongoing window that forbids checks executions. The next execution of a target falls after the window, or after the last of a chain of overlapping windows.
* *Manual checks executions*: `422` "Checks cannot be executed during a maintenance window", for the UI, the API and the AI assistant tools.
* *Manual operations*: the operation policy check of the controllers adds the maintenance windows of the targets of the operation to the other policies. The forbidden modal names the target the window is set on and when it ends. The API answers `403`.
* *Scheduled operations*: the same check runs at the scheduled time. A window that forbids operations makes the scheduled request fail with the reason "maintenance window". A schedule created or changed during such a window gets it among its warnings.

An action that already runs when a window starts is not stopped. Whether to stop it is an open question.

Proof of concept: checks executions in {poc-repo}/pull/67[#67] (Quantum), {poc-repo}/pull/79[#79] (Oban), {poc-repo}/pull/91[#91] (event sourced), operations in {poc-repo}/pull/68[#68] (Quantum), {poc-repo}/pull/80[#80] (Oban), {poc-repo}/pull/92[#92] (event sourced).

==== Storage

The windows are configuration, as schedules and frequencies: they are stored like schedules in each implementation, an Ecto table in the Quantum and Oban implementations and an aggregate per window in the event sourced one. No aggregate can hold the rule they enforce: it depends on the topology, which lives in the host, cluster, database and SAP system aggregates. The coverage and the enforcement are a query and a policy on the read side, shared by the three implementations.

Plan B, the exception window per target (see link:#_plan_b_exception_window_per_target[Plan B: exception window per target]), is the fallback if maintenance windows cannot be delivered.

Proof of concept: {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22maintenance%20windows%22%20sort%3Acreated-asc[`maintenance windows` pull requests], per implementation: {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22maintenance%20windows%22%20label%3A%22scheduling%3A%20quantum%22%20sort%3Acreated-asc[Quantum], {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22maintenance%20windows%22%20label%3A%22scheduling%3A%20oban%22%20sort%3Acreated-asc[Oban], {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22maintenance%20windows%22%20label%3A%22scheduling%3A%20event%20sourced%22%20sort%3Acreated-asc[event sourced], {poc-repo}/pulls?q=is%3Apr%20is%3Aopen%20label%3A%22maintenance%20windows%22%20label%3A%22scheduling%3A%20ui%22%20sort%3Acreated-asc[UI]. The windows are stored in an Ecto table in {poc-repo}/pull/61[#61] (Quantum) and {poc-repo}/pull/73[#73] (Oban), and as an aggregate per window in {poc-repo}/pull/85[#85] (event sourced).

=== HTTP API

The same API serves the three implementations. Times are ISO 8601 in UTC. Every schedule and window carries the IANA timezone used to compute its recurrence.

* `interval`: `"5m"`, `"15m"`, `"30m"`, `"1h"`, `"6h"`, `"12h"`, `"24h"`, `"1w"`, `"2w"`, `"4w"` or `"disabled"`.
* `recurrence`: `{frequency, interval, weekdays, ends_on, max_occurrences}`, or null for a one-time schedule. `frequency` is `daily`, `weekly`, `monthly` or `yearly`. `weekdays` uses ISO numbers, Monday is 1. `ends_on` is a date, excluded.
* `forbids`: a non empty subset of `checks_execution` and `operations`.

|===

|`GET /api/v1/settings/checks_execution` | |`{interval, enforced_from_env}`
|`PUT /api/v1/settings/checks_execution` |`{interval}` |the same shape. `409` when enforced from the environment
|`GET /api/v1/hosts/:id/checks/schedule`, `GET /api/v1/clusters/:id/checks/schedule` | |`{interval, effective_interval, global_interval, last_requested_at, next_execution_at}`
|`PUT /api/v1/hosts/:id/checks/schedule`, `PUT /api/v1/clusters/:id/checks/schedule` |`{interval}` |the same shape. `interval: null` means the global frequency

A schedule is `{id, target_type, target_id, operation, params, starts_at, timezone, recurrence, next_run_at, occurrences, bulk_id, created_by, inserted_at, updated_at}`. `target_type` is `host`, `cluster`, `sap_system` or `database`. A warning is `{message, metadata}`: the message of a policy that does not pass now, and the resources it names.

A window is `{id, target_type, target_id, target_name, starts_at, timezone, duration_minutes, recurrence, forbids, bulk_id, created_by, inserted_at, updated_at, inherited, active, current_occurrence, next_occurrence}`. `target_type` is `host`, `cluster`, `database` or `sap_system`. `inherited` tells that the window is set on another target that covers the requested one, named by `target_name`. An occurrence is `{starts_at, ends_at}`.

Errors: `403` without the ability of the operation, or of the maintenance windows, `404` for an unknown target, schedule or window, `422` for a past start, an operation that is not schedulable, params that the immediate request refuses, or an invalid recurrence or window. A manual checks execution during a maintenance window that forbids it gets `422` on the existing request endpoints.

Each target type has its own checks schedule actions, so every operation of the API has its own id. The read endpoints are also AI assistant tools.

Live refresh: the topics `monitoring:operation_schedules` (`operation_schedules_changed`, with the target id) and `monitoring:maintenance_windows` (`maintenance_windows_changed`, with the target type and id) tell the UI to fetch the schedules or the windows of the target on display again.

=== Wanda changes

Not required for scheduling, but recommended: Wanda checks the CloudEvent expiration of `OperationRequested`. An expired request is answered with `OperationCompleted` `REQUEST_FAILED` and a new detail value `EXPIRED` (adding a protobuf enum value is backward compatible). Web records it as "Trento not available". Without it, a scheduled operation requested while Wanda or RabbitMQ is down runs whenever Wanda comes back, possibly hours later.

NOTE: `Contracts.from_event(payload, validate_expiration: true)` returns `{:error, :event_expired}` without the decoded message, so it cannot be used as is to reply: Wanda needs the `operation_id` and `group_id`. Wanda decodes the message as today and checks the expiration attribute (`Contracts.attributes_from_event/1`) before starting the operation.

The same validation for `ExecutionRequested` avoids a burst of stale checks executions after a Wanda downtime. No reply is needed there.

== Summary

* Scheduling and maintenance windows live in Trento Web. Wanda and the agent keep their reactive role.
* How schedules are stored and fired is to be decided: keep Quantum (Option 1), Oban (Option 2) or event sourcing (Option 3). The three serve the same API and the same frontend.
* One recurrence module serves operation schedules and maintenance windows.
* Checks: a one minute evaluator applies the global or per target frequency and skips the targets covered by a maintenance window. `CHECKS_INTERVAL` takes the new values, stays compatible, and becomes documented and exposed in helm and ansible.
* Operations: the policies move out of the HTTP plug into a shared context function. They run at creation as information, and at the scheduled time on fresh data. "Already running" is left to Wanda now (Option A). A synchronous check in Web (Option B) is planned with bulk operations.
* Maintenance windows are configuration. The targets they cover are resolved on the read side when needed, and one policy enforces them on manual and scheduled requests, for checks and for operations.
* Bulk scheduling creates one independent schedule per target, and a bulk maintenance window one window per target.
* The exception window per host and cluster stays available as plan B.
* Wanda validates request expiration, so late requests fail cleanly.

== Unresolved questions

* Which implementation stores and fires the schedules: keep Quantum, Oban or event sourcing? TBD.
* Schedules of a deleted or locked user: they keep running, because no permission check runs at fire time. Is that the expected behavior?
* An operation that is no longer schedulable after an upgrade: delete its schedules, or let them fail at fire time?
* What do overviews and dashboard show about schedules and maintenance windows?
* Does a window on a host also forbid the cluster and SAP instance operations that act on that host? The proofs of concept forbid them.
* What happens to a checks execution or an operation that already runs when a window starts? The proofs of concept do not stop it.
* Is the user warned when a new schedule falls in a future window? The proofs of concept warn only about a window that is ongoing when the schedule is saved.
* Does a window have a name or a description? The proofs of concept have none.
* How is the "premium" distinction enforced? The proofs of concept only show a badge.
* The proofs of concept take the simplest alternative for these product questions, to confirm:
** a schedule is saved even when its policies fail at creation
** the grace period is 5 minutes
** a change restarts the count of occurrences, and a missed occurrence counts
** the end date is excluded, for individual and bulk schedules and for windows
** no summary entry for a bulk request
** a window lasts at most 31 days and ends on a date or never, not after a number of occurrences
** windows that ended are not listed
** in the UI, bulk maintenance windows start from the hosts list only. The API accepts every target type
** plan B: an exception window has no end condition
