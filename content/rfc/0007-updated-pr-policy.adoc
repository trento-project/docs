== Summary

The Trento project has started to receive external contributions via pull requests, many of them written with the aid of AI or fully vibe-coded. This RFC proposes changes in the pull request policy to ensure that all contributions, whether internal or external, meet the project's quality standards and maintain the integrity of the codebase.

This proposal introduces a clear and consistent pull request policy for code quality, maintainability, and security, as well as requirements for testing and documentation. It also establishes a pre-review automation gate to ensure that only high-quality contributions are reviewed and merged into the codebase.

== Motivation

Trento is an open-source project that values community contributions, that is the basis for commercial products that are offered to customers with support. However, the influx of AI-generated code and external contributions has raised concerns about code quality, maintainability, and security. This RFC aims to establish a clear and consistent pull request policy that applies to all contributors, ensuring that the project remains robust and reliable.

The amount of time spent by maintainers reviewing low-quality or AI-generated code has increased significantly, which has led to delays in merging contributions and a decrease in the overall quality of the codebase. By implementing a pre-review automation gate and establishing clear guidelines for pull requests, we can reduce the burden on maintainers and ensure that only high-quality contributions are reviewed and merged.

=== Use Cases outline

* As a contributor, I want to understand the expectations for pull requests, so that I can submit code that meets the project's standards.
* As a contributor, I want to be free to use tools that help me write code, including AI-assisted coding tools, so that I can be more productive and efficient without compromising the quality of my contributions.
* As a maintainer, I want to ensure that all contributions, whether internal or external, adhere to the same quality standards, so that the codebase remains maintainable and secure.
* As a maintainer, I want to make sure that the contributions do not introduce vulnerabilities or security risks and do not affect the maintainability of the project, so that the project remains safe for users.
* As a maintainer, I want to ensure that the code is supportable and maintainable, so that future development and maintenance can be carried out effectively.
* As a user of the Trento project, I want to have confidence that the code I use is of high quality and has been reviewed and tested, so that I can rely on it for my own environments.


== Considerations

=== About code responsibility

To protect the maintainer bandwidth while allowing AI tool:

1.  You wrote it, you own it: You are responsible for the code you submit, regardless of whether it was written by you or generated by an AI tool. It is your responsibility to ensure that the code meets the project's quality standards and does not introduce vulnerabilities or security risks. Claiming that the code is AI-generated does not eliminate the responsibility and it is a red flag for existing and future PR. You are expected to review and test the code before submitting it, and to address any issues that arise during the review process.
2. Zero tolerance Triage Rule: Maintainers will immediately close - without review of explanations - any PR exhibiting standard AI hallucinations (non-existing API calls, dead imports, phantom config flags, or generic boilerplate code) or any other code that does not meet the project's quality standards. This rule is in place to protect the integrity of the codebase and to ensure that only high-quality contributions are reviewed and merged.
3. Code contributions will be requested to be accompanied by a clear explanation of the code's purpose, functionality, and any relevant context. This will help maintainers understand the code and its intended use, and will facilitate the review process. PRs that do not provide sufficient context or explanation may be closed without review.
4. Code contributions will express in writing in the PR commit that they followed all project guidelines, including code style, testing, and documentation requirements. This will help ensure that all contributions meet the project's quality standards and are consistent with the existing codebase. PRs that do not include this statement may be closed without review.

=== Pre-Review Automation Gate
To avoid unnecessary maintainer bandwidth consumption, a pre-review automation gate will be implemented to automatically check for code quality, maintainability, and security issues before a pull request is assigned to a maintainer for review. This gate will help ensure that only high-quality contributions are reviewed and merged into the codebase.

== Component changes

=== Addition of CONTRIBUTION.adoc file
The contribution guide will be enhanced with the following sections:
Scope and workflow:
- **Issue first**: PR for new features or structural changes must be linked to an existing issue. PRs without an issue will be closed without review.
- **Keep PRs small and focused**: Pull requests should be limited in scope to a single feature, bug fix, or improvement. Large or multi-purpose PRs may be closed without review. PR bigger than 500 lines of code will be closed without review unless there is previous agreement about it.


=== Pre-Review Automation Gate

Maintainers will not be required to review pull requests that do not meet the project's quality standards. A pre-review automation gate will be implemented to automatically check for code quality, maintainability, and security issues before a pull request is assigned to a maintainer for review. This gate will help ensure that only high-quality contributions are reviewed and merged into the codebase.

=== Policy on AI-Assisted Submissions
We permit the use of AI tools (e.g., GitHub Copilot, ChatGPT, Claude) to assist in writing code and documentation, subject to strict accountability rules:

1. **Mandatory Disclosure:** You must disclose whether AI tools were used to generate any portion of the code, tests, or PR description.
2. **Full Verification:** You must manually compile, run, and test all AI-generated code. Submitting code you do not fully understand or have not personally executed is prohibited.
3. **Quality Bar:** PRs containing "AI slop"—such as hallucinated methods, invalid dependencies, or generic fluff in PR descriptions—will be closed immediately, tagged as `invalid`, and may result in a ban for repeat occurrences.
4. **Licensing Integrity:** You certify that any AI-generated code submitted complies with our project license and does not introduce copyrighted third-party material.

We will follow the Linux Foundation's AI Code of Conduct and the Open Source Initiative's AI Guidelines to ensure that all contributions, whether internal or external, meet the project's quality standards and maintain the integrity of the codebase. For that reason, we will add the following section to the CONTRIBUTION.adoc file:

    Code or other content generated in whole or in part using AI tools can be contributed to Trento. However, there are some unique considerations related to AI generated content that developers should factor into their contributions. 

    Contributors should ensure that the terms and conditions of the generative AI tool do not place any contractual restrictions on how the tool’s output can be used that are inconsistent with the project’s open source software license, the project’s intellectual property policies, or the Open Source Definition. 
    If any pre-existing copyrighted materials (including pre-existing open source code) authored or owned by third parties are included in the AI tool’s output, prior to contributing such output to the project, the Contributor should confirm that they have have permission from the third party owners–such as the form of an open source license or public domain declaration that complies with the project’s licensing policies–to use and modify such pre-existing materials and contribute them to the project. Additionally, the contributor should provide notice and attribution of such third party rights, along with information about the applicable license terms, with their contribution.
    Some tools provide features that can assist contributors. For example, some tools provide a feature that suppresses responses that are similar  to third party materials in the AI tool’s output, or a  feature that flags similarity between copyrighted training data or other materials owned by third parties and the AI tool’s output and provides information about the licensing terms that apply to such third party materials.

- [ ] I have run and passed all automated tests and linters locally.
- [ ] I have added tests that cover my changes.
- [ ] I have updated relevant documentation.

*Please select one of the following:*

- [ ] **No AI tools** were used in generating this code, PR description, or tests.
- [ ] **AI tools were used** as an assistant in preparing this PR.
- Tools used: `____________________`
- [ ] **I certify that I have manually reviewed, run, and tested all changes in a local environment.**
- [ ] **I understand how every line of submitted code functions and take full personal responsibility for its maintenance, licensing compliance, and technical validity.**

=== Review comments

Our review process is as follows:
- Automation checks that the PR is succesfully passing all tests and linters. No human review will be performed until all automated checks pass.
- The questionnaire needs to be fully completed, including the AI usage disclosure section. PRs that do not comply will be flagged for correction before review.
- The human reviewer will trigger GitHub Copilot or any other AI tool to assist in the review process.
- If all the previous steps are completed, the reviewer will leave comments on the PR using the Conventional Comments format.
- At the end of the review, the reviewer will wait for the comments to be addressed and will then approve the PR if all issues have been resolved. If the PR is not approved, the reviewer will provide feedback on what needs to be changed before it can be approved.


Our comments follows the guidelines from Conventional Comments (https://conventionalcomments.org/). The following are examples of how to use the different types of comments:

Comments follow the following format:
<label> [decorations]: subject

* label - This is a single label that signifies what kind of comment is being left.
* subject - This is the main message of the comment.
* decorations (optional) - These are extra decorating labels for the comment. They are surrounded by parentheses and comma-separated.
* discussion (optional) - This contains supporting statements, context, reasoning, and anything else to help communicate the “why” and “next steps” for resolving the comment.

.Labels used
[width="100%",cols="<18%s,<82%", ]
|===
|Label| Description

|praise|	Praises highlight something positive. Try to leave at least one of these comments per review. Do not leave false praise (which can actually be damaging). Do look for something to sincerely praise.
|nitpick|	Nitpicks are trivial preference-based requests. These should be non-blocking by nature.
|suggestion|	Suggestions propose improvements to the current subject. It’s important to be explicit and clear on what is being suggested and why it is an improvement. Consider using patches and the blocking or non-blocking decorations to further communicate your intent.
|issue|	Issues highlight specific problems with the subject under review. These problems can be user-facing or behind the scenes. It is strongly recommended to pair this comment with a suggestion. If you are not sure if a problem exists or not, consider leaving a question.
|todo|	TODO’s are small, trivial, but necessary changes. Distinguishing todo comments from issues: or suggestions: helps direct the reader’s attention to comments requiring more involvement.
|question|	Questions are appropriate if you have a potential concern but are not quite sure if it’s relevant or not. Asking the author for clarification or investigation can lead to a quick resolution.
|thought|	Thoughts represent an idea that popped up from reviewing. These comments are non-blocking by nature, but they are extremely valuable and can lead to more focused initiatives and mentoring opportunities.
|chore|	Chores are simple tasks that must be done before the subject can be “officially” accepted. Usually, these comments reference some common process. Try to leave a link to the process description so that the reader knows how to resolve the chore.
|note|	Notes are always non-blocking and simply highlight something the reader should take note of.
|===

After a review is completed, the reviewer should leave a summary comment that includes a list of all the comments made during the review. This summary comment should also include any additional context or information that may be helpful for the author to understand the feedback and make necessary changes. If the reviewer has no comments to leave, they should still leave a summary comment indicating that the review is complete and that no issues were found. This helps to ensure that the author knows that their work has been reviewed and that they can move forward with confidence.


== Recommended checks for PR
- The PR is not longer than 500 lines of code, unless there is a prior agreement with the maintainers.
- The code is properly formatted and adheres to the project's coding standards.
- The code is well-documented, with clear and concise comments explaining the purpose and functionality of the code.
- The code has been tested and passes all relevant tests, including unit tests, integration tests, and end-to-end tests.

=== Merge Strategies
To avoid polluting the main branch history with reviews, PRs should use the squash merge strategy. This will ensure that the main branch history remains clean and easy to read, while still preserving the individual commits in the PR for reference.
