== Summary

The Trento project is an open source project that is open to receiving external contributions via pull requests. However, with the rise of generative AI, some contributions are submitted with minimal human review. This RFC proposes changes in the pull request policy to ensure that all contributions, whether internal or external, meet the project's quality standards and maintain the integrity of the codebase.

This proposal introduces a clear and consistent pull request policy for code quality, maintainability, and security, as well as requirements for testing and documentation. It also establishes a pre-review automation gate to ensure that only high-quality contributions are reviewed and merged into the codebase.

== Motivation

Trento is an open-source project that values community contributions, and at the same time is used as the core for commercially available solutions intended for use in high stakes production environments. Although the use of AI-generated code is welcomed, in some cases it has raised concerns about code quality, maintainability, and security. This RFC aims to establish a clear and consistent pull request policy that applies to all contributors, ensuring that the project remains robust and reliable, and open to anybody willing to contribute.

The amount of time spent by maintainers reviewing low-quality or AI-generated code has increased significantly in the last monthts, which has led to delays in merging contributions and a decrease in overall project efficiency. By implementing a pre-review automation gate and establishing clear guidelines for pull requests, we can reduce the burden on maintainers and ensure that only high-quality contributions are reviewed and merged.

=== Use Cases outline

* As a user, I want to have confidence that the code I use is of high quality and has been reviewed and tested, so that I can rely on it for my own environments.
* As a user of the Trento project, I want to have confidence in the maintainability, supportability and security of the codebase, so that I can trust that it will meet the quality standards I require in production and that fixes can be made timely.
* As a contributor, I want to understand the expectations for pull requests, so that I can submit code that meets the project's standards.
* As a contributor, I want to be free to use tools that help me write code, including AI-assisted coding tools, so that I can be more productive and efficient without compromising the quality of my contributions.
* As a maintainer, I want to ensure that all contributions, whether internal or external, adhere to the same quality standards, so that the codebase remains maintainable and secure.
* As a maintainer, I want to make sure that the contributions do not introduce vulnerabilities or security risks and do not affect the maintainability of the project, so that the project remains safe for users.
* As a maintainer, I want to ensure that the code is supportable and maintainable, so that future development and maintenance can be carried out effectively.
* As a maintainer, I want to have enough context about the PR to understand the rationale behind the changes, and participate in the design and refinement conversation when they are needed.

== Considerations
The following considerations should be added to the code standards. Whenever possible, they also should be included in the workflows to create PR (for instance, with specific templates, pre-commit hooks, and CI/CD checks).

In general, code contributors and reviewers should follow the guidelines outlined in `CONTRIBUTING.adoc`.

=== About code responsibility

The following rules apply to all code contributions.  These rules are in place to protect the integrity of the codebase and to ensure that only high-quality contributions are reviewed and merged. Submitting code to the project implies that you have read and understood these rules, and that you agree to them:

1. *You wrote it, you own it*: You are responsible for all the code you submit, regardless of whether it was written by you or generated by an AI tool. It is your responsibility to ensure that the code meets the project's quality standards and does not introduce vulnerabilities or security risks. Claiming that the code is AI-generated does not eliminate the responsibility and it is a red flag for _existing and future_ PR. You are expected to review and test the code before submitting it, and to address any issues that arise during the review process.
2. *Zero tolerance Triage Rule*: Maintainers will immediately close - _without review of explanations_ - any PR exhibiting standard AI hallucinations (non-existing API calls, dead imports, phantom config flags, or generic boilerplate code) or any other code that does not meet the project's quality standards.
3. *Code contributions will be accompanied by a clear explanation of the code's purpose, functionality, and any relevant context*. You should not expect reviewers to guess the rationale for the code. This will help maintainers understand the code and its intended use, and will facilitate the review process. _PRs that do not provide sufficient context or explanation may be closed without review_.
4. *Code contributions will express in writing in the PR commit that they followed all project guidelines, including code style, testing, and documentation requirements*. This will help ensure that all contributions meet the project's quality standards and are consistent with the existing codebase. PRs that do not include this statement may be closed without review.

=== How Fast should code reviews be?

If you are not in the middle of a focused task, you should do a code review shortly after it comes in.
One business day is the maximum time it should take to respond to a code review request (i.e., first thing the next morning). When we talk about the speed of code reviews, it is the response time that we are concerned with, as opposed to how long it takes a CL to get through the whole review and be submitted. The whole process should also be fast, ideally, but it’s even more important for the individual responses to come quickly than it is for the whole process to happen rapidly.
Following these guidelines means that a typical CL should get multiple rounds of review (if needed) within a single day.

There is one time where the consideration of personal velocity trumps team velocity. If you are in the middle of a focused task, such as writing code, don’t interrupt yourself to do a code review. Research has shown that it can take a long time for a developer to get back into a smooth flow of development after being interrupted. So interrupting yourself while coding is actually more expensive to the team than making another developer wait a bit for a code review.

Instead, wait for a break point in your work before you respond to a request for review. This could be when your current coding task is completed, after lunch, returning from a meeting, coming back from the breakroom, etc.


== Updated Pull Request Workflow (for reviewers)

=== Step 0: Pre-work
Before a PR is submitted, the developer needs to have a clear understaning of the scope and requirements. If refinement work is needed, consider both including the refinement documentation as context in the PR and choosing reviewers that have participated in the refinement and design of the solution. For that reason, it is important to involve the relevant stakeholders early in the process to ensure that the PR is well-informed and aligned with the project's goals.

=== Step 1: Initial assignment
The PR can be assigned to a squad (preferably) or to one or several individuals, or left unassigned for maintainers to pick up. In the last case where it is left unassigned, maintainers will review the PR and assign it to the appropriate person or team for further review and action. Unless it is specifically requested, the PR needs to have one successful maintainer review before merging and no rejections, so assigning it to a squad will generally help streamline this process. AI approval does not replace the requirement for a human maintainer review.

=== Step 2: Take a broad view of the change
Look at the PR description and what the PR does in general. Does this change even make sense? If this change shouldn't have happened in the first place, please respond immediately with an explanation and why the change should not be happening. It is a good idea to suggest to the developer what they should have done instead.

If the code is not understandable, it is clearly not ready for review or it manifests AI hallucinations, it should be immediately flagged and the PR should be closed. The developer can open a new pull request after addressing the issues.

=== Step 3: Pre-review automation gate
Once step 1 is done, the reviewer will include an AI-assisted verification step to automatically check for code quality, maintainability, and security issues. This step will help ensure that only high-quality contributions proceed to the manual review stage. Step 1 will ensure that AI is not engaged inappropriately or without proper oversight.

=== Step 4: Manual review
After the automatic verification step is successfully completed, the reviewer will manually review the code changes. This includes checking for correctness, adherence to project guidelines, code readability, and overall quality. The reviewer will provide feedback, request changes if necessary, and approve the pull request once it meets all standards.
During this phase, AI-assisted verification tools may still be used to support the review process, but the final judgment and approval rest with the human reviewer.

When the AI identifies the PR as low risk and trivial, and if the CI is passing, the reviewer may choose to expedite the approval process, potentially merging the PR with minimal manual intervention. In order to do so, the reviewer should document the rationale for the expedited approval in the PR comments, ensuring transparency and traceability for future reference. If the merge of the PR imples that the build is broken, additional CI tests will need to be put in place to avoid errors in the future.

It is foreseeable that CI test suite will have to be improved to reduce the likelihood of breaking the build when trivial or low-risk PRs are merged with minimal manual intervention and to avoid regressions.

=== Step 4: Merge

Once the PR has passed all required reviews and checks, and any necessary changes have been made, the reviewer or maintainer will approve the PR. The writer of the code will proceed to merge the PR into the main branch. The merge should be done in a way that maintains the integrity of the project’s history and ensures that the CI tests continue to pass.

If the PR was expedited due to being low risk and trivial, the rationale for the expedited merge should be documented in the PR comments, as mentioned in Step 3. After merging, it is important to monitor the CI results to catch any unexpected issues early. We should evaluate the possibility of automatically merging dependabot updates if they meet the low-risk and trivial criteria.

If the PR addresses a critical bug or security vulnerability, the developer will be responsible for ensuring that the code can be merged into the release branch for backporting.

== Alternative workflows for PR review
=== Dependency Review

We use automatic tools to discover and analyze dependencies in the project. This helps identify outdated, vulnerable, or otherwise problematic dependencies early in the development process, allowing maintainers to address potential issues before they affect the codebase.

In the case of dependency updates, the maintainers will verify that all the updated dependencies are compatible with the project, do not introduce new vulnerabilities, and adhere to the project's quality standards before merging the changes. Code reviews should be fast and efficient, focusing on making sure that the dependency updates do not break the project or introduce new issues, and that all the tests are passing.

Changes in dependencies due to deprecated versions or changes of API will require manual update and intervention by the maintainers. Minor updates that do not introduce breaking changes can be handled more efficiently, but still require verification to ensure compatibility and stability.

=== When is ok to create a large PR?
There are a few situations in which large changes aren’t as bad:

* You can usually count deletion of an entire file as being just one line of change, because it doesn’t take the reviewer very long to review.
* Sometimes a large CL has been generated by an automatic refactoring tool that you trust completely, and the reviewer’s job is just to verify and say that they really do want the change. These CLs can be larger, although some of the caveats from above (such as merging and testing) still apply.


=== Approve PRs

A key point here is that there is no such thing as “perfect” code—there is only better code. Reviewers should not require the author to polish every tiny piece of a CL before granting approval. Rather, the reviewer should balance out the need to make forward progress compared to the importance of the changes they are suggesting. Instead of seeking perfection, what a reviewer should seek is continuous improvement. A CL that, as a whole, improves the maintainability, readability, and understandability of the system shouldn’t be delayed for days or weeks because it isn’t “perfect.”

Reviewers should always feel free to leave comments expressing that something could be better, but if it’s not very important, prefix it with something like “Nit: “ to let the author know that it’s just a point of polish that they could choose to ignore.

== Pre-Review Automation Gate
To avoid unnecessary maintainer bandwidth consumption, a pre-review automation gate will be implemented to automatically check for code quality, maintainability, and security issues before a pull request is assigned to a maintainer for review. This gate will help ensure that only high-quality contributions are reviewed and merged into the codebase.

1. *Manual Trigger*: To avoid unnecessary CI/CD costs, this gate will be triggered manually by a maintainer after the initial triage.
2. *Maintainers won't perform human reviews until 100% of automated checks pass*: Once the automation gate is passed, the pull requests will have passed all automated checks (linter, tests, commit linting, PR size, PR template completion, etc).
3. *AI-best practices configuration*: The project will include guidelines and configurations to ensure that AI-assisted contributions adhere to best practices, including proper disclosure, verification, and quality standards. Including architecture documents for AI, AI skills and other relevant documentation will be part of this configuration.

== Component changes

=== Addition of CONTRIBUTING.adoc file
The contribution guide will be enhanced with the following sections:
Scope and workflow:
- **Issue first**: PR for new features or structural changes must be linked to an existing issue. PRs without an issue will be closed without review.
- **Keep PRs small and focused**: Pull requests should be limited in scope to a single feature, bug fix, or improvement. Large or multi-purpose PRs may be closed without review. PR bigger than 500 lines of code will be closed without review unless there is previous agreement about it.

=== Policy on AI-Assisted Submissions
We permit the use of AI tools (e.g., GitHub Copilot, ChatGPT, Claude) to assist in writing code and documentation, subject to strict accountability rules:

1. **Mandatory Disclosure:** You must disclose whether AI tools were used to generate any portion of the code, tests, or PR description.
2. **Full Verification:** You must manually compile, run, and test all AI-generated code. Submitting code you do not fully understand or have not personally executed is prohibited.
3. **Quality Bar:** PRs containing "AI slop"—such as hallucinated methods, invalid dependencies, or generic fluff in PR descriptions—will be closed immediately, tagged as `invalid`, and may result in a ban to the user for repeated occurrences.
4. **Licensing Integrity:** You certify that any AI-generated code submitted complies with our project license and does not introduce copyrighted third-party material.

We will follow the Linux Foundation's AI Code of Conduct and the Open Source Initiative's AI Guidelines to ensure that all contributions, whether internal or external, meet the project's quality standards and maintain the integrity of the codebase. For that reason, we will add the following section to the CONTRIBUTING.adoc file:

    Code or other content generated in whole or in part using AI tools can be contributed to Trento. However, there are some unique considerations related to AI generated content that developers should factor into their contributions. 

    Contributors should ensure that the terms and conditions of the generative AI tool do not place any contractual restrictions on how the tool’s output can be used that are inconsistent with the project’s open source software license, the project’s intellectual property policies, or the Open Source Definition. 
    If any pre-existing copyrighted materials (including pre-existing open source code) authored or owned by third parties are included in the AI tool’s output, prior to contributing such output to the project, the Contributor should confirm that they have permission from the third party owners–such as the form of an open source license or public domain declaration that complies with the project’s licensing policies–to use and modify such pre-existing materials and contribute them to the project. Additionally, the contributor should provide notice and attribution of such third party rights, along with information about the applicable license terms, with their contribution.
    Some tools provide features that can assist contributors. For example, some tools provide a feature that suppresses responses that are similar  to third party materials in the AI tool’s output, or a feature that flags similarity between copyrighted training data or other materials owned by third parties and the AI tool’s output and provides information about the licensing terms that apply to such third party materials.

=== Review comments

Our review process is as follows:
- Automation checks that the PR is successfully passing all tests and linters. No human review will be performed until all automated checks pass.
- The questionnaire needs to be fully completed, including the AI usage disclosure section. PRs that do not comply will be flagged for correction before review.
- The human reviewer will trigger GitHub Copilot or any other AI tool to assist in the review process.
- If all the previous steps are completed, the reviewer will leave comments on the PR using the Conventional Comments format.
- At the end of the review, the reviewer will wait for the comments to be addressed and will then approve the PR if all issues have been resolved. If the PR is not approved, the reviewer will provide feedback on what needs to be changed before it can be approved.

GitHub allows to wrap your code in a suggestion block. By wrapping code in a suggestion block, you provide an exact replacement that the author can apply with a single click:

[source, markdown]
  ```suggestion
  this is my new suggestion
  ```

Our comments follows the guidelines from Conventional Comments (https://conventionalcomments.org/). The following are examples of how to use the different types of comments:

Comments follow the following format:
<label> [decorations]: subject

* *label* - This is a single label that signifies what kind of comment is being left.
* *subject* - This is the main message of the comment.
* *decorations _(optional)_* - These are extra decorating labels for the comment. They are surrounded by parentheses and comma-separated.
* *discussion _(optional)_* - This contains supporting statements, context, reasoning, and anything else to help communicate the “why” and “next steps” for resolving the comment.

.Labels used
[width="100%",cols="<18%,<82%",]
|===
|Label| Description

|praise|	Praises highlight something positive. Try to leave at least one of these comments per review. Do not leave false praise (which can actually be damaging). Do look for something to sincerely praise.
|nitpick or nit|	Nitpicks are trivial preference-based requests. These should be non-blocking by nature.
|suggestion|	Suggestions propose improvements to the current subject. It’s important to be explicit and clear on what is being suggested and why it is an improvement. Consider using patches and the blocking or non-blocking decorations to further communicate your intent.
|issue|	Issues highlight specific problems with the subject under review. These problems can be user-facing or behind the scenes. It is strongly recommended to pair this comment with a suggestion. If you are not sure if a problem exists or not, consider leaving a question.
|todo|	TODO’s are small, trivial, but necessary changes. Distinguishing todo comments from issues: or suggestions: helps direct the reader’s attention to comments requiring more involvement.
|question|	Questions are appropriate if you have a potential concern but are not quite sure if it’s relevant or not. Asking the author for clarification or investigation can lead to a quick resolution.
|thought|	Thoughts represent an idea that popped up from reviewing. These comments are non-blocking by nature, but they are extremely valuable and can lead to more focused initiatives and mentoring opportunities.
|chore|	Chores are simple tasks that must be done before the subject can be “officially” accepted. Usually, these comments reference some common process. Try to leave a link to the process description so that the reader knows how to resolve the chore.
|note|	Notes are always non-blocking and simply highlight something the reader should take note of.
|===

After a review is completed, the reviewer should leave a summary comment that includes a list of all the comments made during the review. This summary comment should also include any additional context or information that may be helpful for the author to understand the feedback and make necessary changes. If the reviewer has no comments to leave, they should still leave a summary comment indicating that the review is complete and that no issues were found. This helps to ensure that the author knows that their work has been reviewed and that they can move forward with confidence.


== Recommended checks for PR
- The PR is not too long, ideally lower than 100 lines and no more than 500 lines unless there is a prior agreement with the maintainers. If your PR is too long, considering using https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/[stacked pull requests]
- The code is properly formatted and adheres to the project's coding standards.
- The code is well-documented, with clear and concise comments explaining the purpose and functionality of the code.
- The code has appropriate unit testing coverage.
- The code has been tested and passes all relevant tests, including unit tests, integration tests, and end-to-end tests.
- The code isn't more complex than it needs to be.
- The developer isn't implementing things that they _might_ need in the future but don't know they need now.

=== Merge Strategies
To avoid polluting the main branch history with reviews, PRs should use the squash merge strategy. This will ensure that the main branch history remains clean and easy to read, while still preserving the individual commits in the PR for reference.

It is recommended to:

* Rewrite your branch history to make it easy to review your changes. This includes squashing fixup commits, rebasing on top of the latest master, and rewriting commits to make them self-contained.
* Use https://github.com/tummychow/git-absorb[git absorb] to automatically create and squash fixup commits.
* Use the https://docs.github.com/en/github/collaborating-with-issues-and-pull-requests/about-pull-request-merges#squash-and-merge-your-pull-request-commits[squash and merge] option to merge your PR.
